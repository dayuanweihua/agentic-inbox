## 1. 目标与验收结果

统一管理多个网站的客服邮箱，例如：

```text
support@project-a.com
support@project-b.com
support@project-c.com
```

上线后的完整链路：

```text
客户 → support@项目域名
         ↓
Cloudflare Email Routing
         ↓
同一份 Agentic Inbox Worker
         ├── 按完整 support 地址归档到独立 Mailbox（SQLite + R2）
         ├── 触发对应 Mailbox 的 AI 草稿
         └── 转发原始邮件到统一 Gmail
                         ↓
                 Gmail 标签分类与人工回复
                         ↓
                 Cloudflare SMTP 发信
                         ↓
客户看到 From: 对应项目 Support <support@项目域名>
```

必须同时满足以下验收条件：

- 所有白名单内的 `support@域名` 来信都进入统一 Gmail。
- 同一封来信也保存在对应的 Agentic Inbox Mailbox 中。
- Gmail 回复时客户看到对应项目的 `support@域名`，看不到个人 Gmail 地址。
- 各项目在 Gmail 中使用独立标签，在 Agentic Inbox 中使用独立 Mailbox。
- Worker 使用 SMTP envelope recipient 选择 Mailbox，不能依赖可伪造或缺失的邮件头 `To`。
- 非白名单收件地址不创建 Mailbox、不归档、不转发。
- Agentic Inbox 后台受 Cloudflare Access 保护。
- 每个发件域名的 SPF、DKIM、DMARC 均通过外部邮箱实测。

## 2. 范围、假设与取舍

### 2.1 实施假设

- 所有项目域名使用 Cloudflare DNS，且最好处于同一个 Cloudflare Account。
- 统一收件地址为一个可正常登录的 Gmail；本文以 `yourname@gmail.com` 占位。
- 每个网站第一阶段只接入明确的 `support@域名`，不启用 catch-all。
- Gmail 是日常客服主工作台；Agentic Inbox 用于副本归档、AI 草稿、搜索和 MCP。
- 需要向任意客户地址发信，因此生产环境启用 Workers Paid 和 Email Sending。
- 第一阶段由同一位管理员访问全部 Mailbox，不要求每邮箱独立成员权限。

部署前必须将本文所有以下占位符替换为真实值：

```text
yourname@gmail.com
project-a.com
project-b.com
inbox.admin-domain.com
```

### 2.2 为什么保留 Agentic Inbox

如果唯一目标只是“所有 Support 来信进 Gmail，并从 Gmail 用别名回复”，最简单方案是 Email Routing 直接转发 Gmail，完全不需要部署 Agentic Inbox。

本方案保留 Agentic Inbox，是为了同时获得：

- 每邮箱独立 Durable Object + SQLite 归档；
- R2 附件存储；
- AI 自动草拟回复；
- 跨邮件搜索与独立网页客户端；
- MCP 接入外部 Agent。

### 2.3 唯一数据主入口

第一阶段应只在 Gmail 完成人工回复。原因是：

```text
Gmail → Cloudflare SMTP → 客户
```

这条链路不经过 Agentic Inbox，所以 Gmail 发出的回复不会自动写入 Agentic Inbox 的 Sent 文件夹。当前阶段的数据关系是：

| 数据 | Gmail | Agentic Inbox |
|---|---|---|
| 客户来信 | 完整 | 完整 |
| Gmail 人工回复 | 完整 | 不自动同步 |
| Agentic Inbox 内发送 | Gmail 不一定存在 | 完整 |
| AI 草稿 | 不自动同步 | 完整 |

不要同时在两个后台回复同一封邮件。若将来要求 Agentic Inbox 拥有完整收发历史，见第 14 节二期方案。

## 5. 开发改造方案

原则：只修改邮件入口、收件识别、环境类型、Wrangler 配置和对应测试；不改前端，不实现额外的多用户权限系统。

### 5.1 配置设计

在 `wrangler.jsonc` 中新增统一转发地址，并明确所有域名与 Support 白名单：

```jsonc
"vars": {
  "DOMAINS": "project-a.com,project-b.com,project-c.com",
  "EMAIL_ADDRESSES": [
    "support@project-a.com",
    "support@project-b.com",
    "support@project-c.com"
  ],
  "FORWARD_TO_EMAIL": "yourname@gmail.com"
}
```

同时收紧 Agentic Inbox 自身的发信地址：

```jsonc
"send_email": [
  {
    "name": "EMAIL",
    "remote": true,
    "allowed_sender_addresses": [
      "support@project-a.com",
      "support@project-b.com",
      "support@project-c.com"
    ]
  }
]
```

说明：

- `FORWARD_TO_EMAIL` 不是密码，但属于部署环境配置；正式值可放 Wrangler vars 或 Dashboard 变量。
- `POLICY_AUD`、`TEAM_DOMAIN` 继续使用 Worker secrets，不提交真实值。
- Gmail 使用的 Cloudflare SMTP API Token 只保存在 Gmail 的 SMTP 配置中，绝不能写入仓库或 Worker vars。
- Wrangler 配置是生产配置的 source of truth，避免同时在 Dashboard 和仓库中维护不同值。

### 5.2 环境类型

`FORWARD_TO_EMAIL` 由 `wrangler types` 从 `wrangler.jsonc` 自动生成到 `Cloudflare.Env`，因此不在 `workers/types.ts` 中重复声明；该文件只保留项目自有的 Access secret 类型：

```ts
POLICY_AUD: string;
TEAM_DOMAIN: string;
```

修改 Wrangler 配置后运行 `npm run cf-typegen`，让生成的 `Cloudflare.Env` 与配置保持一致。

### 5.3 正确使用 envelope recipient

当前 `receiveEmail()` 已接收完整的 `ForwardableEmailMessage`，并使用 envelope recipient：

```ts
const mailboxId = message.to.trim().toLowerCase();
```

`message.to` 是 SMTP envelope 的 `RCPT TO`，才是 Cloudflare 实际路由到 Worker 的地址。邮件头 `To` 仍可用于界面展示，但不能用于授权和 Mailbox 选择。

处理顺序：

1. 检查 `message.to` 是否为合法邮箱。
2. 检查其是否存在于 `EMAIL_ADDRESSES`。
3. 检查 R2 中的 `mailboxes/{mailboxId}.json` 是否存在。
4. 检查 `FORWARD_TO_EMAIL` 非空。
5. 解析并保存邮件与附件。
6. 转发原始邮件到 Gmail。
7. 触发 AI 自动草稿。

白名单是生产硬边界。`EMAIL_ADDRESSES` 为空时，生产环境应拒绝或记录错误，不应退化成“接受任意地址”。本地开发可保留宽松行为，但应明确区分环境。

### 5.4 转发 Gmail

`workers/app.ts` 的邮件 handler 应接收 `ForwardableEmailMessage` 并把完整事件交给 `receiveEmail()`；`workers/index.ts` 在成功归档后调用：

```ts
await message.forward(env.FORWARD_TO_EMAIL);
```

转发目标必须先在 Cloudflare Email Routing 的 Destination Addresses 中验证。Cloudflare 官方 `ForwardableEmailMessage` 同时提供 `to`、`raw`、`rawSize` 与 `forward()`，参考：[Workers Email Handler API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/)。

建议保留错误抛出，让 Cloudflare 能记录并重试失败投递；同时在日志中记录以下非敏感字段：

```text
message-id
envelope from
envelope to
mailboxId
forward destination（可掩码）
archive result
forward result
```

不得记录正文、附件内容、Access JWT 或 SMTP Token。

### 5.5 一致性与失败策略

归档和转发不是数据库事务，必须明确主次：

- Gmail 投递是主目标。
- Agentic Inbox 归档是增强能力。
- 白名单或 Mailbox 不存在属于配置错误，应拒绝处理并告警，不能静默吞信。
- 转发失败必须抛错，交给 Cloudflare 处理失败投递。
- 归档成功、转发重试时可能产生重复归档；应使用原始 `Message-ID + mailboxId` 做幂等键，而不是每次重试都生成随机 UUID。

最小可上线版本可以先接受极低概率重复，再在上线前压测和故障注入中确认；推荐正式上线前完成 Message-ID 幂等，避免重试制造重复邮件和重复 AI 草稿。

### 5.6 建议的文件级变更清单

| 文件 | 变更 |
|---|---|
| `workers/app.ts` | 使用完整邮件事件类型；将事件传给收件函数；统一记录和抛出处理错误 |
| `workers/index.ts` | 用 `message.to` 选 Mailbox；执行白名单；保存后转发；增加幂等保护 |
| `workers/types.ts` | 保留 Access secret 类型；邮件变量由 Wrangler 生成的 `Cloudflare.Env` 提供 |
| `wrangler.jsonc` | 配置多域名、Support 白名单、Gmail 目标与 sender allowlist |
| `.dev.vars.example` | 增加本地变量示例，不放真实凭证 |
| 邮件入口测试文件 | 覆盖 envelope、白名单、转发、重试与多域名隔离 |
| `README.md` | 增加本项目分支的 Gmail 转发说明 |

## 6. 开发验收测试

### 6.1 单元/集成测试矩阵

| 场景 | 输入 | 预期 |
|---|---|---|
| 合法 Support | envelope to 在白名单且 Mailbox 存在 | 归档一次、转发一次、AI 触发一次 |

## 7. Cloudflare 前置准备

### 7.1 套餐与费用

截至 2026-07-11，Cloudflare 官方说明：

- Email Routing 收件在 Workers Free/Paid 均为不限量。
- 向任意外部地址发信需要 Workers Paid。
- Workers Paid 每个账号每月包含 3,000 封外发邮件，超出后 `$0.35/1,000` 封。
- 转发到账号内已验证 Destination Address 免费，不计入外发额度。

费用应在正式实施当天再次核对：[Cloudflare Email Service Pricing](https://developers.cloudflare.com/email-service/platform/pricing/)。此外还可能产生 Workers、Durable Objects、R2 与 Workers AI 用量费用。

### 7.2 域名条件

每个域名必须：

- 使用 Cloudflare DNS；
- 分别 Onboard Email Routing；
- 若要从该域名发信，分别 Onboard Email Sending；
- 不与现有 MX 邮件服务产生冲突。

Email Routing 与 Email Sending 是两套独立配置和 DNS 记录，官方说明见：[Domain configuration](https://developers.cloudflare.com/email-service/configuration/domains/)。如果域名正在使用 Google Workspace、Microsoft 365 或其他 MX 服务，不要直接切换，先评估迁移与停机影响。

## 8. 部署 Agentic Inbox

### 8.1 建议的仓库与环境

```text
代码仓库：自己的私有仓库
Worker 名称：agentic-inbox
管理后台：inbox.admin-domain.com
生产分支：main
```

不要把 Cloudflare API Token、Access 值或个人 Gmail 写入公开仓库。建议先用一个测试域名完成全链路，再批量增加其他域名。

### 8.2 安装与静态检查

```bash
npm ci
npm run typecheck
npm run build
```

### 8.3 创建 R2

如果自动部署没有创建：

```bash
npx wrangler r2 bucket create agentic-inbox
```

核对 `wrangler.jsonc` 中 `bucket_name` 与实际名称一致。

### 8.4 配置 Access secrets

先在 Worker 的 Domains & Routes 中启用 One-click Cloudflare Access，只允许管理员 Gmail 登录。获取 Access 提供的值后执行：

```bash
npx wrangler secret put POLICY_AUD
npx wrangler secret put TEAM_DOMAIN
```

生产环境缺少这两个值时，当前代码会 fail closed。任何通过同一 Access Policy 的成员都能访问全部 Mailbox 和 `/mcp`，当前项目没有 per-mailbox authorization。

### 8.5 部署

```bash
npm run deploy
```

部署后先访问 Worker URL，确认：

- 未登录会进入 Access；
- 非授权账号无法访问；
- 授权账号可以打开前端；
- `/api/v1/config` 返回预期域名和邮箱白名单。

## 9. 配置统一 Gmail Destination

进入 Cloudflare：

```text
Compute → Email Service → Email Routing → Destination Addresses
```

添加 `yourname@gmail.com`，然后在 Gmail 中打开 Cloudflare 验证邮件并完成验证。Destination Address 在账号级共享，可供同一账号下多个域名重复使用。参考：[Route emails](https://developers.cloudflare.com/email-service/get-started/route-emails/)。

此处验证的是 Worker `message.forward()` 的合法目标，不等同于 Gmail 的 Send mail as 验证；两次验证都要完成。

## 10. 为每个域名配置收信

对每个域名分别执行：

```text
Compute → Email Service → Email Routing → Onboard Domain
```

等待 Routing DNS 状态正常后创建显式规则：

```text
Email pattern: support
Action: Send to a Worker
Destination: agentic-inbox
```

例如：

```text
support@project-a.com → agentic-inbox Worker
support@project-b.com → agentic-inbox Worker
```

不要再为同一个 `support@域名` 创建“直接转发 Gmail”的并行规则。邮件必须先进入 Worker，再由 Worker 保存并转发。

第一阶段不建议 catch-all，原因是它会把拼错地址和无关地址也送入 Worker。新增地址时，应同时完成：

1. `EMAIL_ADDRESSES` 白名单更新；
2. `allowed_sender_addresses` 更新；
3. Cloudflare Routing 规则；
4. Agentic Inbox Mailbox 创建；
5. Gmail Send mail as；
6. Gmail 标签过滤器；
7. 外部端到端测试。

## 11. 为每个域名配置发信

对每个域名分别进入：

```text
Compute → Email Service → Email Sending → Onboard Domain
```

Cloudflare 会配置用于发送的 bounce MX、SPF、DKIM 与 DMARC。DNS 一般数分钟生效，但官方提示最长可能需要 24 小时。不要把“认证记录已配置”理解为“一定进入收件箱”；域名信誉、内容、退信和投诉仍会影响投递。

新域名建议 DMARC 从监控策略开始，在确认所有合法发信源通过后再逐步收紧。实施时以 Dashboard 生成的记录为准，不手工复制本文示例值。

## 12. Gmail 统一工作台配置

### 12.1 创建 Cloudflare SMTP Token

在 Cloudflare 创建最小权限 API Token：

```text
Account permission: Email Sending → Edit
Resource: 仅目标 Cloudflare Account
```

Cloudflare SMTP 当前参数：

```text
SMTP Server: smtp.mx.cloudflare.net
Port: 465
Security: SSL / Implicit TLS
Username: api_token
Password: Cloudflare Email Sending API Token
```

`api_token` 是固定字面值；端口 587/STARTTLS 不受支持。SMTP 当前仍标为 Beta，投产前应再次核对：[Cloudflare SMTP reference](https://developers.cloudflare.com/email-service/api/send-emails/smtp/)。单封 SMTP 邮件含 MIME 编码后的上限为 5 MiB，大附件使用 R2/Drive 链接。

### 12.2 为每个 Support 地址添加 Send mail as

Gmail 网页端：

```text
设置 → 查看所有设置 → 账号和导入 → 用这个地址发送邮件 → 添加另一个电子邮件地址
```

逐个添加：

```text
Project A Support <support@project-a.com>
Project B Support <support@project-b.com>
```

填写上一节 SMTP 参数。Gmail 会向 Support 地址发验证邮件；该邮件会按本方案进入 Worker、Agentic Inbox 并转发回 Gmail。打开邮件完成验证。

Gmail 官方支持最多 99 个 Send mail as 地址，参考：[Send emails from a different address or alias](https://support.google.com/mail/answer/22370)。

### 12.3 自动选择原收件地址

在 Gmail 的 Send mail as 设置中选择：

```text
回复邮件时 → 使用收到邮件时所用的地址回复
```

每次正式发送前仍应检查编辑器的 `From`：

```text
From: Project A Support <support@project-a.com>
To: customer@example.com
```

为每个 Send mail as 地址设置相同的 Reply-To 地址，即 `support@同域名`。不要设置个人 Gmail 为 Reply-To。

注意：Gmail 官方提示某些客户端可能显示“on behalf of”，自动回复、过滤器自动响应或邮箱异常通知也可能暴露原 Gmail。必须用 Gmail、Outlook 等不同客户端实测显示效果。

### 12.4 Gmail 标签和过滤器

建议标签：

```text
Support/Project A
Support/Project B
Support/Project C
```

为每个地址创建过滤器：

```text
to:(support@project-a.com)
→ 应用标签 Support/Project A
```

转发邮件若在 Gmail 中无法稳定匹配 `to:`，改用 Cloudflare Worker 转发时添加的自定义头，例如 `X-Original-Recipient`，或根据 Gmail 实际保留的 Delivered-To/原始收件头调整过滤条件。先查看一封真实转发邮件的“显示原始邮件”，再固定过滤器。

## 13. Agentic Inbox 初始化

登录受 Access 保护的管理后台，为白名单内每个地址创建 Mailbox：

```text
Name: Project A Support
Email: support@project-a.com
```

```text
Name: Project B Support
Email: support@project-b.com
```

必须在切换 Routing 规则前创建 Mailbox。当前代码遇到白名单内但不存在的 Mailbox 会忽略来信；开发改造应将其改成可观测的配置错误。

每个 Mailbox 可配置不同的：

- `fromName`；
- 签名；
- AI system prompt；
- 产品背景和不可承诺事项。

示例 AI 提示词：

```text
You are the support drafting assistant for Project A.
Draft concise replies using the Project A product policy.
Never promise refunds, credits, deadlines, or legal outcomes without human approval.
Do not send email automatically. A human must review every draft.
```

## 14. 二期：让 Agentic Inbox 拥有完整会话

如果未来需要 Agentic Inbox 也记录 Gmail 发出的回复，只选择一种方案实施：

### 方案 A：统一改为 Agentic Inbox 回复（推荐）

- Gmail 只做通知和只读副本；
- 人工在 Agentic Inbox 审核 AI 草稿并发送；
- Sent、Thread、附件和 AI 上下文都在同一系统；
- 最符合项目原始架构。

### 方案 B：同步 Gmail Sent（当前已实施）

- 使用独立 Google Cloud 项目和 `gmail.readonly` OAuth；
- Worker Cron 每 5 分钟增量查询 Gmail Sent；
- 仅导入 From 与 Mailbox 完全相同的业务邮件；
- 使用 Message-ID 去重，并通过 In-Reply-To/References 映射线程；
- refresh token 保存在 R2 私有对象，Settings 提供连接、手动同步与撤权；
- 具体启用与验收见 `docs/Gmail-Sent同步配置.md`。

### 方案 C：Gmail 回复自动 BCC 回系统

- 表面简单，但容易形成路由循环、重复线程和错误 Mailbox；
- Gmail 用户也可能忘记 BCC；
- 不建议作为可靠生产方案。

## 15. 端到端上线验收

每个项目必须使用另一个外部邮箱执行，不要只用目标 Gmail 自发自收。

### 15.1 收件

外部邮箱发送：

```text
To: support@project-a.com
Subject: E2E project-a 001
Attachment: 小于 1 MiB 的测试文件
```

确认：

- Gmail 在合理时间内收到；
- Gmail 标签正确；
- Agentic Inbox 的 Project A Mailbox 仅出现一封；
- 正文与附件两端都可读；
- Project B Mailbox 没有该邮件；
- AI 只生成草稿，没有自动发送。

### 15.2 回复身份与线程

在 Gmail 回复，发送前确认 `From`。客户侧确认：

- From 为 `support@project-a.com`；
- Reply-To 为 `support@project-a.com`；
- 看不到 `yourname@gmail.com`；
- 回复仍进入原会话；
- 查看原始邮件时 SPF、DKIM、DMARC 均 PASS。

### 15.3 跨项目防串号

分别给 A、B 两个 Support 地址发信并回复，确认：

```text
Project A 客户 ← support@project-a.com
Project B 客户 ← support@project-b.com
```

### 15.4 故障演练

- 临时配置错误的 Gmail Destination，确认日志和失败投递可见。
- 使用非白名单地址，确认不进入任何 Mailbox/Gmail。
- 发送 BCC 或邮件头 `To` 与 envelope 不一致的邮件，确认仍按 envelope 路由。
- 重投同一 Message-ID，确认不会产生重复 AI 草稿。
- 使用超过 SMTP 5 MiB 的回复附件，确认 Gmail 明确报错并改用链接。

## 16. 上线顺序与回滚

### 16.1 灰度上线

1. 选一个低流量测试域名。
2. 完成代码改造、类型检查、构建与部署。
3. 验证 Gmail Destination、Sending Domain 和 SMTP。
4. 创建 Agentic Mailbox 和 Gmail Send mail as。
5. 将该域名的 `support` Routing 规则切到 Worker。
6. 连续完成收件、回复、附件、跨客户端认证测试。
7. 观察 24 小时日志后再逐个接入其他域名。

### 16.2 回滚方案

若 Worker 转发异常，对受影响域名执行：

1. 暂停指向 Worker 的 `support` Routing 规则。
2. 临时改为 `support@域名 → 已验证 Gmail Destination` 直接转发。
3. Gmail Send mail as 与 SMTP 保持不变，客服仍可收发。
4. 修复 Worker 后先用测试域名验证，再恢复 Worker Routing。

直接转发回滚会暂停 Agentic Inbox 归档与 AI 草稿，但能优先保证 Gmail 收件。

## 17. 日常运维

每周：

- 检查 Email Routing 与 Email Sending 日志；
- 检查失败、退信、抑制列表和垃圾投诉；
- 抽查 Gmail 回复 From 是否正确；
- 检查 AI 是否只草拟、不自动发送。

每月：

- 检查 Workers、Email Sending、DO、R2、AI 用量；
- 审核 Cloudflare Access 成员；
- 清理离职或不再需要的访问权；
- 检查 SMTP API Token 有效期与权限范围；
- 备份或制定 R2/DO 数据导出策略。

安全要求：

- SMTP Token 不进入 Git、日志、截图和前端。
- Cloudflare Access 是当前唯一用户权限边界。
- `/mcp` 与网页使用同一 Access 边界，授权 MCP 等同授权全部 Mailbox。
- 不在日志记录邮件正文和附件。
- 每个 AI 草稿必须人工确认，不启用未经审核的自动发送。
